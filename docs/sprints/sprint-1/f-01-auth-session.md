## 1. Feature-Level Software Design Specification (Feature SDS)

### 1.1 Overview and Workflow
`F-01` establishes real backend authentication and stateful session management for both `ORGANIZER` and `PARTICIPANT` actors:
1. **Login (`POST /api/auth/login`):** Validates email and password input, looks up the user by email in PostgreSQL, verifies the plaintext password against `user.passwordHash` using `bcryptjs` (`bcrypt.compare`), generates a 64-character hex session token via `crypto.randomBytes(32).toString('hex')`, creates a new `Session` row in PostgreSQL with an 8-hour expiration (`expiresAt = now + 8h`), sets an `httpOnly` cookie (`sid`), and returns the sanitized user profile (`id`, `email`, `name`, `role`).
2. **Current User Retrieval (`GET /api/auth/me`):** Reads the `sid` cookie, queries PostgreSQL for the `Session` joined with `User`, verifies `session.expiresAt > now`, and returns the authenticated user's profile. If the cookie is missing, unknown, or expired, returns `401 Unauthorized`.
3. **Logout (`POST /api/auth/logout`):** Deletes the active `Session` record from PostgreSQL, clears the `sid` cookie, and returns `200 OK`. Subsequent requests using the old session cookie are rejected with `401 Unauthorized`.

### 1.2 Dependencies
- PostgreSQL database via Prisma ORM (`User` and `Session` models).
- `bcryptjs` (cost factor >= 10) for password hashing and verification.
- Node.js built-in `node:crypto` (`crypto.randomBytes(32).toString('hex')`) for cryptographically random session tokens.
- Reproducible seed script (`prisma/seed.ts`) reading `SEED_ORGANIZER_PASSWORD` and `SEED_PARTICIPANT_PASSWORD` from environment variables.

### 1.3 Validation, Boundary Cases, and Security Rules
- Missing or malformed `email` or empty `password` on login returns `400 Bad Request`.
- Unknown email or mismatched password returns `401 Unauthorized` with a generic error message (`"Invalid email or password"`) to prevent user enumeration.
- `passwordHash` is never included in any API response payload or server log (`NFR-01`).
- Expired sessions (`expiresAt <= now`) are rejected with `401 Unauthorized` and cleaned up (`NFR-02`).
- Client-supplied headers or body fields attempting to spoof `userId` or `role` are ignored; identity is derived strictly from the server-side `Session` record (`NFR-02`).

## 2. UI, API, and Data Specifications

### 2.1 UI Behavior
- **Login Screen (`/login`):** Email and password inputs, submit button with loading state (`"Signing in..."`), and inline error alert for `400`/`401` responses.
- **Navigation Header:** Displays authenticated user's `name`, `role` badge (`ORGANIZER` or `PARTICIPANT`), and a **Logout** button.
- **Session Guard:** On app load, calls `GET /api/auth/me`. Unauthenticated users attempting to view protected screens are redirected to `/login`.

### 2.2 API Endpoint Specifications

| Method & Path | Auth Required | Request Body / Cookie | Success Response | Error Responses |
|---|---|---|---|---|
| `POST /api/auth/login` | Public | Body: `{ "email": string, "password": string }` | `200 OK` + `Set-Cookie: sid=<token>; HttpOnly; Path=/; SameSite=Lax`<br>`{ "user": { "id": string, "email": string, "name": string, "role": "ORGANIZER" \| "PARTICIPANT" } }` | `400` validation error<br>`401 { "error": "Invalid email or password" }` |
| `GET /api/auth/me` | Authenticated (`ORGANIZER`, `PARTICIPANT`) | Cookie: `sid=<token>` | `200 OK`<br>`{ "user": { "id": string, "email": string, "name": string, "role": "ORGANIZER" \| "PARTICIPANT" } }` | `401 { "error": "Authentication required" }` |
| `POST /api/auth/logout` | Authenticated (`ORGANIZER`, `PARTICIPANT`) | Cookie: `sid=<token>` | `200 OK` + clears `sid` cookie<br>`{ "message": "Logged out" }` | `401 { "error": "Authentication required" }` |

### 2.3 Data Model and Constraints (Prisma / PostgreSQL)
- **`Role` Enum:** `ORGANIZER`, `PARTICIPANT`
- **`User` Table:**
  - `id` (`UUID`, Primary Key)
  - `email` (`String`, Unique, Not Null)
  - `name` (`String`, Not Null)
  - `passwordHash` (`String`, Not Null)
  - `role` (`Role`, Not Null)
  - `createdAt` (`DateTime`, default `now()`)
- **`Session` Table:**
  - `id` (`String` / opaque 64-hex token generated by `crypto.randomBytes(32).toString('hex')`, Primary Key)
  - `userId` (`UUID`, Foreign Key -> `User.id` `ON DELETE CASCADE`, Indexed)
  - `expiresAt` (`DateTime`, Not Null)
  - `createdAt` (`DateTime`, default `now()`)

## 3. Acceptance Criteria (`AC`)

| AC ID | Criterion (Observable Expected Outcome) | Linked Req |
|---|---|---|
| **AC-F01-01** | Given a seeded user (`ORGANIZER` or `PARTICIPANT`), when `POST /api/auth/login` is called with valid email and password, then the server responds `200 OK`, sets an `httpOnly` `sid` cookie (`crypto.randomBytes(32).toString('hex')`), creates a `Session` record in PostgreSQL with an 8-hour expiry, and returns `{ user: { id, email, name, role } }` without `passwordHash`. | `FR-01`, `NFR-01`, `NFR-02` |
| **AC-F01-02** | Given an invalid password or unknown email, when `POST /api/auth/login` is called, then the server responds `401 Unauthorized`, sets no session cookie, and creates no `Session` row in PostgreSQL. | `FR-01`, `NFR-02` |
| **AC-F01-03** | Given a valid active `sid` cookie, when `GET /api/auth/me` is called, then the server responds `200 OK` with the authenticated user's `{ id, email, name, role }`. | `FR-01`, `NFR-02` |
| **AC-F01-04** | Given no `sid` cookie or an unrecognized token, when `GET /api/auth/me` is called, then the server responds `401 Unauthorized` without returning user data. | `FR-01`, `NFR-02` |
| **AC-F01-05** | Given a logged-in session, when `POST /api/auth/logout` is called, then the `Session` row is removed from PostgreSQL, the cookie is cleared, and a subsequent `GET /api/auth/me` using the old cookie returns `401 Unauthorized`. | `FR-01`, `NFR-02`, `NFR-04` |
| **AC-F01-06** | Given a `Session` row in PostgreSQL whose `expiresAt` timestamp is in the past, when `GET /api/auth/me` is called with that session's cookie, then the server responds `401 Unauthorized`. | `NFR-02` |
| **AC-F01-07** | Given a login request with an empty/missing `email` or empty/missing `password`, when `POST /api/auth/login` is called, then the server responds `400 Bad Request` with a validation error message and creates no `Session` row in PostgreSQL. | `FR-01` |

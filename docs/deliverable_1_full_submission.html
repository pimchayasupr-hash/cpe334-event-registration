1. Stakeholder Problem, Chosen Context, Scope, and Explicit Exclusions

1.1 Stakeholder Problem and Chosen Context

In a university faculty setting, academic departments, research labs, and student academic committees frequently organize hands-on technical workshops and guest seminars with strict room capacity limits (ranging from small 20-seat computer labs to 500-seat auditoriums). Currently, organizers rely on shared spreadsheets or generic web forms that lack real-time seat enforcement and role-based access control. As a result, popular workshops suffer from overbooking when multiple students submit forms for the last remaining seats at the same time, duplicate entries by the same student, premature sign-ups before event details are finalized, and privacy breaches when participant rosters are exposed to unauthorized students or other organizers.

1.2 Product Scope

The Faculty Event Registration and Attendance System provides an end-to-end web platform across three sprints:
  • Sprint 1 (Deliverable 1 Baseline): Authenticated ORGANIZER and PARTICIPANT workflows; creating events in DRAFT state and explicitly publishing them (PUBLISHED) with validated positive capacity (1..500) and future start time; safe capacity adjustments; discovering published events; participant seat registration with strict capacity and duplicate-registration prevention (including concurrent requests for the final seat); viewing own registrations; and organizer inspection of their own event's registrant roster.
  • Sprint 2 (Core Expansion): Participant registration cancellation with seat release, registration deadline enforcement, organizer event editing/closing workflows, and event search/filtering.
  • Sprint 3 (Completion and Hardening): On-site participant check-in, attendance status recording (PRESENT / ABSENT), and event attendance summary/reporting.

1.3 Explicit Exclusions

  • No Paid Ticketing or Payment Processing: All faculty workshops and seminars are free university activities; payment gateways and billing are excluded.
  • No External Messaging Gateways: Email, SMS, or push notification services are excluded; confirmation and status updates are displayed directly in the web UI.
  • No Self-Registration or Password Recovery in Sprint 1: User accounts are provisioned via reproducible database seed scripts reading passwords from environment variables; self-service sign-up, email verification, password reset, and multi-role assignment per user are excluded from Sprint 1.
  • No Waiting List / Auto-Promotion: When an event reaches full capacity, new registration attempts are rejected immediately rather than queued on a waitlist.

6. Security, Authentication, and Session Lifecycle

6.1 Credential Protection & Password Hashing (NFR-01)

  • Stored passwords use salted bcrypt hashes generated via bcryptjs with a cost factor of 10.
  • Application queries explicitly omit passwordHash from SELECT projections (select: { id: true, email: true, name: true, role: true }).
  • Pre-commit checklists ensure zero passwords, connection strings, or .env files enter Git commits (R-12).

6.2 Stateful Session Token Lifecycle (NFR-02)

1. Creation: Upon successful credential validation, the server generates 32 cryptographically secure random bytes formatted as a 64-character hexadecimal string (crypto.randomBytes(32).toString('hex')). 2. Storage: The token is inserted into PostgreSQL with expiresAt = now() + 8 hours. 3. Transmission: Set via HTTP cookie named sid with flags: HttpOnly, Path=/, SameSite=Lax, and Secure (in production/HTTPS environments). 4. Verification Middleware: For every incoming protected request, the server reads req.cookies.sid, queries the Session table, and verifies expiresAt > now(). If expired, the session row is deleted and 401 Unauthorized is returned. 5. Revocation (Logout): Deletes the Session record from PostgreSQL and clears the sid cookie. Subsequent requests with that token fail immediately.

7. Concurrency Architecture and Last-Seat Allocation (BR-04, NFR-03)

7.1 The Last-Seat Race Condition Problem

When multiple participants submit registration requests simultaneously for an event that has only 1 seat remaining, naive application logic (reading active count, then executing an insert) creates a classic Read-Modify-Write race condition, leading to catastrophic room overbooking.

7.2 Pessimistic Row-Locking Mechanism

To prevent overbooking, registration requests run inside an atomic PostgreSQL transaction using Pessimistic Row-Level Locking: `typescript // Architectural Implementation Pattern for Concurrency Protection await prisma.$transaction(async (tx) => { // 1. Acquire exclusive row-level lock on the target Event row const [event] = await tx.$queryRaw> SELECT id, status, capacity FROM "Event" WHERE id = ${eventId}::uuid FOR UPDATE ; if (!event || event.status !== 'PUBLISHED') { throw new NotFoundOrConflictError('Event not open for registration'); } // 2. Check for duplicate registration by the same participant const existing = await tx.registration.findUnique({ where: { eventId_userId: { eventId, userId: currentUser.id } } }); if (existing) { throw new DuplicateRegistrationError('Already registered for this event'); } // 3. Count current ACTIVE registrations inside the lock boundary const activeCount = await tx.registration.count({ where: { eventId, status: 'ACTIVE' } }); // 4. Invariant check: activeCount must be strictly less than capacity if (activeCount >= event.capacity) { throw new CapacityExceededError('Event is at full capacity'); } // 5. Persist the registration row atomically return await tx.registration.create({ data: { eventId, userId: currentUser.id, status: 'ACTIVE' } }); }); ` Guarantees:
  • Only one transaction acquires the lock on the Event row at any instant; concurrent transactions block until the holding transaction finishes.
  • The next transaction in queue reads the updated activeCount, immediately detects activeCount >= capacity, and aborts with 409 Conflict.
  • Overbooking is mathematically impossible under any level of concurrency.

1.1 Overview and Workflow

F-01 establishes real backend authentication and stateful session management for both ORGANIZER and PARTICIPANT actors: 1.   • Reproducible seed script (prisma/seed.ts) reading SEED_ORGANIZER_PASSWORD and SEED_PARTICIPANT_PASSWORD from environment variables.

1.3 Validation, Boundary Cases, and Security Rules

  • Missing or malformed email or empty password on login returns 400 Bad Request.
  • Unknown email or mismatched password returns 401 Unauthorized with a generic error message ("Invalid email or password") to prevent user enumeration.
  • passwordHash is never included in any API response payload or server log (NFR-01).
  • Expired sessions (expiresAt <= now) are rejected with 401 Unauthorized and cleaned up (NFR-02).
  • Client-supplied headers or body fields attempting to spoof userId or role are ignored; identity is derived strictly from the server-side Session record (NFR-02).

1. Feature-Level Software Design Specification (Feature SDS)

1.1 Overview and Workflow

F-03 allows authenticated PARTICIPANT users to register for PUBLISHED workshops/seminars and inspect their own persisted registrations while guaranteeing zero overbooking and zero duplicate active registrations: 1. Submit Registration (POST /api/events/:id/registrations): - Requires an authenticated PARTICIPANT (BR-06). - Runs inside an interactive PostgreSQL transaction (prisma.$transaction) that acquires a row-level exclusive lock on the target Event record (SELECT id, status, capacity FROM "Event" WHERE id = $1 FOR UPDATE) to serialize concurrent requests targeting the same event (BR-04, NFR-03). - Verifies that the event exists and has status == 'PUBLISHED' (if DRAFT or non-existent, rejects with 404 Not Found / 409 Conflict per BR-03). - Checks whether a registration already exists for (eventId, userId) (additionally enforced by the PostgreSQL composite unique constraint @@unique([eventId, userId]) per BR-05 and AD-05); if present, aborts with 409 Conflict ("Already registered for this event"). - Counts ACTIVE registrations for eventId. If activeCount >= event.capacity, aborts with 409 Conflict ("Event is at full capacity"). - Inserts a new Registration row with status = 'ACTIVE' and commits, returning 201 Created. 2. View Own Registrations (GET /api/registrations/me): - Requires an authenticated PARTICIPANT (BR-06). - Queries Registration strictly filtered by userId = currentUser.id (BR-07), joined with the associated Event summary (id, title, category, location, startAt, endAt, capacity), ordered by createdAt DESC.

1.2 Validation, Boundary Cases, and Permissions

  • Full capacity boundary (BR-04): When activeCount == capacity - 1, one registration succeeds (activeCount becomes capacity); the next registration attempt returns 409 Conflict.

  • Duplicate registration (BR-05, AD-05): A second request from the same PARTICIPANT for the same event returns 409 Conflict without creating a second row. (Per AD-05, Sprint 1 has no cancellation; Sprint 2 will migrate the unique constraint to a partial index on status = 'ACTIVE'.)
  • Role & Privacy (BR-06, BR-07): Unauthenticated calls return 401 Unauthorized. ORGANIZER calls to POST /api/events/:id/registrations or GET /api/registrations/me return 403 Forbidden. No endpoint allows a participant to query another user's userId.

  // 1. Create a 1-seat event
  const concurrencyEvent = await prisma.event.create({
    data: {
      title: 'Extreme Concurrency Test Workshop',
      description: 'Race condition simulation',
      category: EventCategory.WORKSHOP,
      location: 'Room 101',
      startAt: new Date(Date.now() + 48  3600  1000),
      endAt: new Date(Date.now() + 50  3600  1000),
      capacity: 1,
      status: EventStatus.PUBLISHED,
      organizerId,
    },
  });


// 2. Prepare 5 distinct participant accounts and sessions
  const participantSids: string[] = [];
  for (let i = 1; i <= 5; i++) {
    const user = await prisma.user.create({
      data: {
        email: race.student.${i}@kmutt.ac.th,
        name: Race Participant ${i},
        passwordHash: 'hash',
        role: Role.PARTICIPANT,
      },

    const sid = crypto.randomBytes(32).toString('hex');
    await prisma.session.create({
      data: { id: sid, userId: user.id, expiresAt: new Date(Date.now() + 3600  1000) },
    });
    participantSids.push(sid);

// 3. Fire 5 simultaneous requests via Promise.all

const responses = await Promise.all(promises);
